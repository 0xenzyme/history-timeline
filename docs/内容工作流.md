# 内容生产与自动准入

状态：2026-11-07 接受的工作流；第一段实现事件新增发布与存量修订。人物生产、只读体检入口和一次性资产整理尚未实施。

## 范围与规则

用户指定范围并手动选择 Coding Agent 和模型。执行会话研究、起草和预检后交接；另一独立审核会话核对并调用准入工具应用。只有一道自动准入门槛：全部必需检查通过的候选自动进入正式源文件；其余进入 pending。没有固定两次用户审批。用户负责角色交接，并处理需要取舍的异常；交接不等于内容批准，未回答不构成取舍决定。

人物事实遵循 `pipeline/PLAYBOOK.md`，事件事实遵循《事件线规则》，告警解释遵循《内容质量》。本文件定义执行协议，不改变领域语义。brief、未知生年以及未维护的作品、经历等可选内容仍可以合法发布；不计算完整度评分，不按数量补写史实。

新事件发布和存量事件修订均按当前准入标准检查整个候选。存量未参与本批次的内容保持原样。一次性资产整理中发现未达新门槛的已发布内容，先形成候选和问题清单；纠正、撤下与引用处理按具体范围决定，不自动撤下全库。

## 材料位置

| 路径 | 职责 |
| --- | --- |
| `workspace/content/raw/<batch-id>/batch.json` | 本批次候选、证据与审核的权威工作材料；完成后保留必要内容依据 |
| `workspace/content/raw/<batch-id>/accepted.json` | 已接受候选与独立审核的固定副本；后续修订使用新批次，保留原依据 |
| `workspace/content/raw/<batch-id>/result.json` | 最新准入、应用和验证结果；不是执行日志 |
| `workspace/content/pending/<batch-id>/batch.json` | 未通过项的可重试子集；应用时合回原批次，不丢已完成项 |
| `workspace/content/pending/<batch-id>/reasons.json` | 每个未通过项的原因；以最新 check 结果为准 |
| 现有 `content/` 与适用的 `pipeline/` 文件 | 唯一 canonical 来源 |
| `public/data/` | pipeline 生成的运行数据，不手改 |

`workspace/content/` 不随站点公开，并由 Git 忽略。它保存跨聊天复查所需的必要材料；不要删除已完成批次的史料依据。canonical 中的书目出处继续随正式内容版本化。临时检索输出可放批次子目录，无须全部保留。未来如需共享批次依据，应单独导出或明确纳入版本控制，不能误称当前本地材料已备份。

raw 是输入档案，不是永远未审核的状态标记；最终状态以 result 和实际文件为准。审核接受、源文件已应用、编译验证通过分别报告。pending 中的材料不能被 pipeline 当成正式内容。

## 单一准入门槛

1. 用户授权范围明确；候选 id 在范围内，新增和修订操作准确。
2. 独立审核者核对收录理由、全部已维护事实、原始出处、必要摘录、异说和不确定性；结论为 pass。起草者不能自审。
3. parser、schema、领域 lint、候选集投影与引用检查通过。新建和重新整理的事件须清除自身 warning；无关存量 warning 可保留，但不能新增其他未解释 warning。
4. 写入前目标仍与候选 before 一致；目标已等于 after 时按已应用恢复，不重复写入。
5. 应用后编译并运行完整 build。失败时明确报告已应用但未验证，保留源文件与依据，修复后重跑；不得声称已完成，也不自动回滚他人的并发修改。

代码检查书目数量、claim 映射与审核快照是否齐全；独立审核 Agent 判断摘录是否支持事实、书目是否独立、收录是否合理。工具不会验证 reviewer 字符串背后是否真是独立会话，也不能证明引用真实。用户将批次交给未起草该候选的独立会话。执行者不自动启动审核、不填写 pass；审核者记录实际核对结论。缺少审核仍不能应用。

审核结论绑定完整 proposal（候选前后原文、证据和 claim），不使用源码哈希、Run id 或 checkpoint revision。改变 proposal 后旧审核失效。每次应用仍重新执行确定性检查，不复用过期的全库检查结论。

## 人工交接入口

执行入口为 `.agents/skills/event-production/SKILL.md`，审核入口为 `.agents/skills/event-review/SKILL.md`。任何 Coding Agent 都可读取相同文件和命令；宿主没有 Skill 发现机制时，用户可以直接提供 SKILL.md 路径。

不配置 agent/model 路由，不开发调用适配器，不自动更换模型。用户选择工具、模型和独立会话；author/reviewer 是可追溯的角色或会话标识，不是模型名称或身份认证。模型与 Agent 名称仅在实际已知时附于角色说明，无须猜测，工具不验证模型是否不同。

1. 执行者准备候选并运行 preflight；通过后给出批次绝对路径、修改摘要和审核交接提示，停止在 awaiting-review。尚无 review 是正常待审状态，不需要制造 pass 才能做机器预检。
2. 用户将批次路径交给独立审核会话。审核者逐项核对并写 review；候选需要修改时返回明确问题，自己不改 proposal。
3. 审核者运行完整 check/apply，工具自动应用通过项并保存 pending。用户不用再逐条批准，也不手写或搬运 JSON。
4. 用户把未通过批次交回执行者补证。修改 proposal 后移除该项旧 review，重新预检、交接；已经接受的历史材料保持原样。用户要求只读检查时不写审核或执行应用。

同一会话中更换模型或角色名不能替代独立审核。执行者已经起草的候选必须交给另一会话；这由操作流程保证，不声称 CLI 能认证模型身份。

## 事件命令

协议和 JSON 结构见 `.agents/skills/event-production/references/contracts.md`。准备批次后：

```bash
# 执行者：只读机器预检，不要求 review，不授予准入
npm run events:production:preflight -- --batch workspace/content/raw/<batch-id>/batch.json

# 审核者：写入实际独立审核结论后检查并应用
npm run events:publish:check -- --batch workspace/content/raw/<batch-id>/batch.json --json
npm run events:production:apply -- --batch workspace/content/raw/<batch-id>/batch.json
```

preflight 和 check 均只读。preflight 的 checksPassed 仅指机器检查，admissionGranted 始终为 false；未应用的成功项显示 awaiting-review，已应用项保留 already-applied。完整 check 继续要求独立审核。apply 重新检查并自动分流，应用所有 ready 项，只生成事件索引，不格式化无关源文件；随后运行 `npm run content` 与 `npm run build`。有 pending 时可部分应用并返回非零退出码；读取结果中的逐项状态，不把非零退出码解释为「完全没有写入」。

新增事件可以从工作区候选直接通过准入，或从已有 canonical draft 发布。候选中的 after 是目标 published 原文，在通过前仅存在于工作区，不是正式发布。既有 published 修订不先退回 draft。旧缺省 status 按 published 识别，修订后的目标显式 published。

依赖被拒绝的新事件不能被其他候选引用。逐项错误支持部分通过；无法安全归因的全局错误（例如组成循环或对其他实体造成的破坏）保守阻止本批次所有候选写入。缩小或修复候选后重试，不能删掉错误绕过检查。

应用使用本地互斥锁防止两个生产工具同时写入；一般编辑器不受锁约束，因此每个目标仍会在写入前比对 before。存在内容冲突时不强制覆盖。索引或验证阶段中断后，重跑同一批次即可检查已写入项并补齐索引、编译和验证。

如进程被强制终止而遗留 `workspace/content/.apply.lock`，先确认记录的 PID 已退出，且无其他内容应用进程，再删除该锁。不要靠删除锁解决仍在运行的生产冲突。

## pending 与恢复

- needs-evidence：自动补证，不能把数据库或重复转引算成独立出处。
- needs-revision：修改候选并重新取得独立审核。
- needs-decision：提出具体史实取舍或范围问题；未得到回答保持 pending。
- reject：保留理由，结束候选；后续只有新证据或明确范围变化才重开。
- conflict：比较当前正式内容与候选，保留并发修改，更新 before/after 后重新审核。

可以用 pending 的 batch.json 重跑同一命令；工具将其合回 raw 权威批次。保持同一批次 scope；扩大授权范围使用新批次 id。修改工作区候选不等于批准，写一个 pass 字段也不代替实际审核。

Harness 只在用户明确要求的大目标中管理交付状态。旧 `.harness/` 资料可作历史证据读取，旧 hash 不成为重开完成阶段的理由。旧 inline 事件迁移仍由其 manifest 管理，与本批次协议分开。

## 首段交付边界与后续检查

本段只提供事件工具和公共协议，不扩写实际历史内容、不迁移旧档案、不改变 UI、不提交或部署。一次性资产整理待小批次效果验证后开展。

任何模型或 Coding Agent 负责执行时，均使用同一协议，并由用户另选独立审核会话。后续检查者直接阅读 batch.json、result.json、pending 原因、canonical 差异和实际编译结果，重点复查史料支持、审核独立性与未决事项；不依赖执行模型的口头完成声明。模型更换本身不改变准入标准。
