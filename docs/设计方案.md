# 历史人物时间轴 · 设计方案

> 版本 v0.3 ｜ 专题：汉代、儒学传承 ｜ 状态：M7 内容管线已落地

## 1. 项目定位

用**生卒年份**作为时间轴，把历史人物串成一张可看、可查、可讲的图。

核心洞察：人物横条（生 → 卒）在同一个年份轴上排开之后，**"谁和谁同时活着"自动成立**，不需要人工标注。汉武帝的 69 年横条、霍去病的 23 年横条、董仲舒横跨到武帝中期的横条——长短交错本身就是历史感。

因此项目有两条基本原则：

1. **重叠是算出来的，关系是人工的。** 生卒年一交汇，"同时代"自动成立；人工只录制真正有意义的关系（君臣、师承、亲族、敌对）。
2. **可以算出来的东西不写进数据。** 父子的先后、朝代的归属，能推导就不录入，保证数据文件精简、可维护。

## 1.1 快速开始

```powershell
npm install
npm run content    # 由 pipeline/ 编译 public/data（改内容后必跑）
npm run dev        # http://localhost:5180
npm run build      # 类型检查 + 管线校验 + 产出 dist/
npm run preview    # 预览构建产物
```

章节可直接深链：`http://localhost:5180/#han/wudi`（`overview` / `hanchu` / `wudi` / `zhaoxuan`）。旧链 `#wudi` 仍指向汉代对应章。儒学传承：`#rujia/overview`、`#rujia/ruhan`。

改内容请改 `pipeline/`（人物登记、专题编排、词表），然后 `npm run content`。`public/data/` 是生成结果，不要手改。

## 2. 信息架构：叙事优先，探索兜底

这是本项目最重要的一个决策。

- **纯工具**（自己缩放、过滤、点人）：自由但"冷"，用户得自己找故事。
- **纯叙事**（章节化的固定镜头）：好读但不可探索。

采用**双层结构**：

- **章节（view）层**：首页按章节呈现，每章预设时间窗、人物集合、事件集合、开场焦点。
  汉代首批 4 章：`汉代全览` / `汉初：布衣天子` / `武帝开疆` / `昭宣中兴`。
- **探索层**：进入章节后，用户可自由缩放、平移、点击人物、切换"显示全部关系"。任何时刻点"复位"回到当前章节的镜头。

章节的透镜机制顺带解决了一个体验难题——**在 3000 年的轴上缩放平移本来就很难用，所以先把镜头摆好，再让用户自己动。**

## 3. 数据模型

站点 = 多个专题的集合。**一个专题 = 一份 JSON**，共用一个渲染器。因此"通史 / 朝代 / 主题 / 中外对照"都只是换数据。

数据由管线编译到 `public/data/<topic>.json`，目录在 `public/data/index.json`，**运行时 fetch，不参与 Vite 构建**。站点不生产内容。

目录 `index.json` 带 `contractVersion: 1`，以及 `regions` / `eras` / `themes` 词表。每个专题条目除 id、标题、文件名外，还有：

- `region`：国家或地区（一个）
- `eras`：朝代或时段（可多值，儒学可同时挂春秋、战国、西汉）
- `themes`：主题（王朝、思想…）

顶栏按这三个分面过滤专题，不做「国家 → 朝代 → 专题」死树。人物 `id` 全局稳定；同一人只在管线登记一次，专题只覆盖泳道和文案。

### 3.1 公元前如何存

存**有符号整数**：前 179 年 → `-179`。显示时格式化成"公元前179年"。

采用历史纪年（不引入天文纪年的公元 0 年），因为面向普通读者，`-1` 表示"公元前1年"比"公元 0 年"更符合直觉。渲染刻度时跳过 0。

### 3.2 年代可信度（四种状态，必须真实呈现）

汉代人物的生卒年大量不可考，如果一律画成实心长条，等于说谎。所以每条横条有四种画法：

| 状态 | 触发条件 | 画法 |
|---|---|---|
| 精确 | `exact` | 实心矩形，两端直角 |
| 约略 | `approx` | 该端 16px 渐隐 |
| 异说 | `disputed` | 该端 16px 渐隐 + 卡片内标注异说原文 |
| 不详 | `unknown` | 该端延伸 **56px 屏幕空间**的渐隐"开放条"，末端加一个朝外的 chevron |

关键点：**开放条的长度是屏幕像素（56px），不是年份。** 因为"生年不详"意味着无界，用年份画会误导成"活了 200 年"；用固定像素画，语义是"知识在此中断"，缩放时长度保持不变。终端 chevron（`⟨` / `⟩`）进一步表明"还在往外延伸，只是不可考"。

> 实践教训：第一版误把开放端写成 `x(生/卒年 ± 55 年)`，导致李广、卫青、卫子夫等条被拉满整屏，视觉上等于说他们活了 200 年。这个 bug 说明该规则必须严格遵守。

典型例子：卫青、李广、霍光、张骞、窦太后生年皆不详，只能画开放条。

### 3.3 泳道分组 ≥ 单列级联

竖轴有两种排法：

- **单列级联**（按生年）：美学最好，关系线统一向右下扫，但人一多就是面条图。
- **泳道分组**（帝王 / 后妃外戚 / 文臣学者 / 武将 / 匈奴）：一眼看出"武将这一道里卫青与霍去病有 11 年重叠"这种**同侪对照**，跨泳道关系线略长。

汉代采用**泳道**，因为汉代的历史张力恰好是"帝王—外戚—武将—儒臣—匈奴"之间的博弈，泳道让结构自己显形。单列级联留给人物少、纯谱系的专题（如儒学传承）。

泳道内按 `order` 或生年排序，一人一行，不打包（保持级联观感）。

## 4. 视觉规范

### 4.1 图层顺序（从下到上）

```
事件时段带 → 年份网格线 → 关系线 → 人物横条 → 人物标签 → 事件竖线/标签
```

关系线压在横条之下，锚点取横条中心，线条从横条底下"钻出来"，视觉最干净。

### 4.2 色彩

- 泳道色 = 人物横条主色（见 lanes）。
- 关系线色 = 关系类型色（见 relationTypes），**敌对用红色虚线**——晁错与窦婴的相争、李广与卫青的嫌隙，性质与君臣线截然不同，必须一眼可分。

### 4.3 事件层两种形态并存

- **时段型（span）**：贯穿全部泳道的低透明度背景色带（汉匈战争 前133–前89、文景之治）。
  表达"时代氛围"。
- **时点型（point）**：竖向虚线 + 顶部标签（前134 罢黜百家）。
  表达"历史锚点"。

事件标签在顶部专用 Ribbon 区，采用**贪心分行**避免重叠：

1. 时点型按年份起点占位；**时段型按标签中心占位**（否则一个长时段会把整行占满，白白浪费空间）。
2. 按起点排序后依次放置，若与同行上一个标签间距小于 10px 则下沉一行，最多 4 行。
3. **4 行都放不下时，不画文字，只保留标记**（竖线 + 三角 pin）。宁可不显示，也不允许文字互相压叠；放大后标签会自动出现。

> 实践教训：第一版在空间不足时会"退回到边缘最小的那一行"强行放置，结果全部 3 行都出现压字。改为"放不下就不画"之后校验为零重叠。

## 5. 交互规范

| 操作 | 行为 |
|---|---|
| 专题切换 | 顶栏标题下拉：按地区、朝代、主题筛选后选专题；写入 `#topicId/viewId` |
| 章节切换 | 设定时间窗 + 人物集 + 事件集 + 焦点，重建布局并重置缩放；写入 URL hash 便于分享 |
| 搜索人物 | 顶栏搜索当前专题的姓名、称号、标签；选中后切到含此人的章节、打开卡片、视野对准生卒 |
| 鼠标滚轮（在绘图区内） | 横向缩放，以指针位置为锚点 |
| Shift / Alt + 滚轮 | 不拦截，交还浏览器上下滚动（人物多时用） |
| 拖动 | 横向平移，限制在专题 `range` 内 |
| ± 按钮 | 以绘图区中心缩放，滚轮不便时的等价入口 |
| Hover 人物 | 高亮该人物 + 其一跳关系线；其余人物降至 22% 透明度；显示 tooltip |
| 点击人物 | 右侧卡片抽屉：生卒（含可信度说明）、简介、标签、关系列表（可点击跳转）、关联事件 |
| 关系全景 | 卡片按钮；以焦点人物为中心画 1 跳关系图（不受当前章节过滤）；点邻居换中心；Esc /「返回时间轴」回到时间轴 |
| 点击空白 | 取消焦点，恢复全部关系隐藏状态 |
| 显示全部关系 | 切换开关，用于探索模式（默认关闭，防止面条图） |
| 复位 | 回到当前章节的镜头 |
| 导出图片 | 把当前视野（时间轴或关系全景）存为 PNG 或 SVG |
| URL hash | `#han/wudi` 可直接深链；旧链 `#wudi` 仍打开汉代对应章 |

### 防面条图三层防御

1. 默认不画任何关系线，点谁亮谁（只亮 1 跳）。
2. 关系类型用线型 + 颜色双重编码。
3. 关系线方向语义化：从生年早的一方弯向晚的一方，师承线自然向学生倾斜。

## 6. 技术方案

**纯前端静态站**，构建产物是 HTML + JS + CSS + JSON，可直接部署到任意静态托管。

| 项 | 选择 | 理由 |
|---|---|---|
| 构建 | Vite 6 + TypeScript | 产物静态，开发体验好 |
| 渲染 | 原生 SVG，手写 | 关系曲线、图层控制、标签不随缩放变形，需要完全控制 |
| 依赖 | `d3-scale` / `d3-zoom` / `d3-selection` | 只取比例尺与缩放，不引入全量 D3 |
| 框架 | 无 | 唯一的 UI 状态就是"当前章节 / 焦点人物 / 缩放域"，不值得上框架 |
| 数据 | 管线编译 `public/data/*.json`，运行时 fetch | 改内容走管线；站点仍一次拉取一份自包含 JSON |

### 6.1 缩放实现关键决策

**不使用 SVG transform 缩放，改为"缩放 → 重算比例尺 → 重绘"。**

原因：如果用 `transform="scale(k)"`，字体和泳道标签会一起被拉伸变形，标签也会跑出可视区。改为每次 zoom 事件读取 `transform.rescaleX(xBase)` 得到新定义域，然后重绘所有 x 相关元素。人物规模在百人级，重绘成本可忽略，换来的是标签始终清晰、泳道标签永远固定在左侧。

渐变（开放条、约略端）使用 `gradientUnits="userSpaceOnUse"` 并以屏幕像素计算端点，因此每次重绘都要重新生成 defs。

### 6.2 用事件委托而非逐元素绑定

SVG 用字符串拼接 + `innerHTML` 一次性写入（性能与简洁度都最好），交互通过**在 svg 根节点上做事件委托**，用 `closest('[data-person]')` 取目标。缩放重绘会重建 DOM，所以重绘后要**重新套用当前的焦点/高亮状态**（状态存在 `state` 里，不依赖 DOM）。

### 6.3 布局按章节重建

`buildLayout(topic, width, view)` 只为本章节可见的人物分配行。章节切换时重建布局，**空泳道会被完全折叠**，不会留下垂直空洞。

> 实践教训：第一版布局全局构建一次、渲染时才过滤人物，结果"昭宣中兴"章节里汉匈泳道的位置留下一大块空白。

### 6.4 本地打开的限制（重要）

`file://` 协议下 `fetch` 本地 JSON 会被浏览器 CORS 拦截。因此：

- 开发：`npm run dev`
- 预览：`npm run build && npm run preview`
- 或任意静态服务器：`python -m http.server`

**不把数据内联进 JS**——运行时仍拉独立 JSON；内容的源文件在 `pipeline/`。

### 6.5 内容管线

渲染器不生产内容。`pipeline/` 负责人物登记、专题编排、词表和把关，编译出契约 JSON。体例见 [`pipeline/PLAYBOOK.md`](../pipeline/PLAYBOOK.md)。

```
选题 → 人物登记（含出处） → 专题编排 → 编译 → 校验 → public/data
```

运行时仍是一份专题一次 fetch。同一人物的生卒只在 `pipeline/registry/people/` 维护；专题文件只写收录、关系和章节。
