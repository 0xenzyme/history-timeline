# 人物收录规则与 PLAYBOOK 审查

- 审查日期：2026-10-01
- 范围：`pipeline/PLAYBOOK.md` 的收录/生卒/关系/章节/文案/polity 口径，及其在 `pipeline/`（compile.ts / lint.ts / infer-taxonomy.ts / types.ts / schema / vocab）的实际落地
- 评判基准（业主给定，本次审查据此打分）：
  1. **尽可能多地收录人物**——规则不应把可考的人挡在门外，规模上限不是目标而是结果
  2. **准确**——年代、归属、身份不能错；宁可标 `unknown` 不可编造

## 1. 总体判断

规则最结实的是**生卒 accuracy 类型系统**（`exact/approx/disputed/unknown` 四态 + 组合校验）与**关系/章节必填约束**——这些是真正「填错即报错」的。

最脆弱的是**底册收录闸门**：固定的「规模检查线」既当不成上限（实际普遍低于下限）又压制收录，且底册的 `exact/approx` 门槛把可考但异说的人挡在门外——同时违反两条原则。另一个系统性缺口是 `person.schema.json` 与真实数据三重不一致且从未被加载，等于没有校验锚点。

关键现状数据：注册人物 **1418** 位；17 个专题；`polity` 单值 1356 / 多值 38 / 缺失 24；accuracy 分布（birth+death 合并）exact 1904、approx 328、unknown 587、disputed 17。

## 2. 结构性问题（按严重度）

### A【high】检查线没有产生有效约束，并可能减少收录数量
- 证据：各专题 `topic.people` 实际数与 PLAYBOOK 检查线对比——短朝应 50–80，但 `qin=31 / sui=23 / zhanguo=37`；中等应 100–160，但 `chunqiu=71 / liangjin=69 / nanbei=59 / sanguo=61 / wudai=62` 全低于 100；唐宋明清应 200–300，但 `tang=179 / ming=132 / yuan=100` 均不足 200。大量专题低于下限。
- 影响：**多收录**。固定人数带在这里被当成了隐性上限，且与现有人数数据严重不符。
- 建议：在《底册层》把检查线从「固定人数带」改为「覆盖七个席位每一格 + 占据该席位的有据可查之人」，作为**下限承诺**而非上下限。

### B【high】`person.schema.json` 与数据/类型不一致，且未被任何校验加载
- 证据：`schema/person.schema.json:6` 用 `additionalProperties:false`，却**没有** `polity/categories/primary/gender/aliases`；而 `pipeline/types.ts:23-28` 定义了它们、`compile.ts:38-44` 也写入运行时。grep 全 `pipeline/` 仅该文件自身含 `person.schema` 字样——**没有任何 load/lint 引用它**。
- 影响：**准确性**（schema 不可信，无法作为校验依据）。
- 建议：要么删掉该文件，要么补齐字段并接入 `content:check`。

### C【medium】底册门槛「exact|approx 生卒」排斥 disputed 与仅活动年者
- 证据：《底册层》条件 2 写「有可引用的生年或卒年（exact 或 approx）」，未列 `disputed`；registry 中 `disputed` 共 17 处。
- 影响：**多收录 + 准确**（`disputed` 是更诚实的标注，但当前规则会排除这类人物）。
- 建议：明确「`disputed` 视为有生卒」；仅有活动年份/朝代者允许以 `approx` 录入而非直接排除。

### D【medium】polity 归属判据与自动推断使用不同原则
- 证据：PLAYBOOK 说 polity 看「被哪个专题收录、和谁发生关系」；但 `infer-taxonomy.ts:86-132` 用 `lane-map + TAG_POLITY_RULES` 关键词从**自由文本 tags** 推断，`232/286` 只在缺失时填。tags 是自由文本，关键词推断可能错标。
- 影响：**准确性**。
- 建议：PLAYBOOK 写明「infer 仅作缺失兜底、不得覆盖手填、自动写入须经人审」，并审计 `TAG_POLITY_RULES` 易误伤项（裸 `'宋'` 已正确处理，其余需复核）。

### E【medium】出处不进运行时 JSON，站点"准确性"无法追溯
- 证据：《出处》节明确只存管线、`compileSearch/compileTopic` 不输出 `sources`。
- 影响：**准确性**（用户无法核对 `exact/disputed` 的根据，后续审校也失去依据）。
- 建议：至少把 `sources` 摘要随人物导出（或独立证据端点）。

### F【medium】阅读层「12–20 人」无执行机制，每专题恰 1 个章省略=全收
- 证据：topic 数据每个专题都有 **1 个 view 不写 `people`**（缺 people 章 = 1），该章收全部 `topic.people`（如 `ming=132`）；`lint.ts` 不校验章人数。
- 影响：多收录和阅读层之间存在冲突（全收章与 12–20 人的阅读层建议不一致）。
- 建议：明确「12–20 仅约束叙事章，全览章允许全收」，并在 lint 校验叙事章上限。

### G【low】PLAYBOOK 数据已漂移
- 称多值 polity「全库约 21 位」，实际 **38 位**（统计 `multi=38`）。
- 建议：更新数字或改为动态计数。

### H【low】两层收录略有循环定义但操作无害
- 底册条件 3「阅读层需要他」依赖章节，章节又属专题。
- 建议：把阅读层定义为「章节内可见」、底册为「专题收录」，强调是不同维度筛选而非嵌套闸门。

## 3. 规则内部矛盾清单

- **矛盾1**：检查线（200–300 上限）与「尽可能多收录」直接对冲；且实际普遍低于下限——既没当上限也没当下限，是失效约束。
- **矛盾2**：底册要求 `exact/approx`，又与「`disputed` 必须写 note 且鼓励诚实标注」并存——`disputed` 的人在底册里既可能被排除又被鼓励。
- **矛盾3**：polity「兴起期归后朝」vs「跨两脉络才多值」的边界（刘邦→`han`、朱元璋→`[yuan,ming]`）靠人判，无操作判据。
- **矛盾4**：阅读层 12–20 与「省略=全收」共存，同一专题两类章标准不同却都合法。

## 4. 规则与实现的落差（纯散文清单）

`lint.ts` 当前只校验：vocab 存在性、relations 必须有 note、views 必须有 brief/focus、sources 非空、accuracy 组合、重复收录、polity **仅校验词表存在**（`lint.ts:21-25`）。

以下规则**零机器校验**：底册三条件、席位门槛、一人一席、阅读层 12–20、polity 归属对错、章节 `from/to` 合理性。也就是——除 accuracy/必填项外，**填错全部静默通过**。

## 5. 建议修改顺序

1. **B**：接回或删除 `person.schema.json`（成本最低，立刻给校验一个锚）。
2. **A + C**：重写检查线为席位覆盖下限 + 明确 `disputed` 计为有效生卒（直接服务"多收录"）。
3. **D + E**：锁定 polity 推断哲学、出处进运行时（服务"准确"）。
4. **F**：章节人数机制与口径澄清。
5. **G/H**：清理漂移与循环措辞。

## 6. 一句话

只改一处时，优先把检查线从固定人数带改为**席位覆盖下限**，并明确 **`disputed` 计为有效生卒**。这样可以减少人数带被误当作上限的问题，也可以避免排除已明确标注异说的人物。
