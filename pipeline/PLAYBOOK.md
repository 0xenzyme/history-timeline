# 内容体例

站点只渲染。人物按专题分目录，例如 `content/qin/ying-zheng.md`。`content/<topic>.md` 是该目录的索引，由 `people:format` 重写，不要手改。同一个人只有一份文件。已经在 `content/qin/` 的人留在那里，包括同时出现在战国、西汉的人。后来迁入的跨专题人物，若 `polity` 里有他所属专题的 id，文件放在其中最晚的专题；否则放在最早的专题，有朝代专题时不放进 `rujia`。还有 44 人留在 `pipeline/registry/people/*.json`：缺 `polity`，或约略年份没有 note。显式 `profile` 过不了校验。不要为了搬迁编造这些字段。专题、泳道、关系、事件、章节和候选台账仍是 JSON。`npm run content` 把两边编译成 `public/data/`。**不要手改 `public/data`。**

```bash
npm run people:new -- qin <id>   # 在该专题目录按简表模板建一个人，并更新索引
npm run people:format            # 把人物 Markdown 收成规定格式，并重写索引
npm run people:check             # 查格式、模板锁、索引和人物规则
npm run content                  # 编译并写入 public/data
npm run content:check            # 校验源数据，并确认生成文件未过期
```

新专题只走管线：候选台账 → 简表登记 → 专题点名 → 需要时再写详表 → 编译。契约是 `contractVersion: 1` 的自包含 JSON；内部登记可以更富（出处、别名、专题文案覆盖）。将来换合同，改编译器，不必重做考证。同一个人只能有一份源文件。

## 原则

两条，同时成立：

1. **尽可能多收。** 席位用来判断谁有资格，不用来规定收多少人。不设专题人数上下限，也不设章节或每一席的人数上限。有可靠年份锚点、又占得到席位的人都收。
2. **准确。** 年份和归属要有史料里站得住的证据。典籍（`classic`）或现代考证（`modern`）可以支撑年份。Wikidata、CBDB 一类数据库只用来发现线索，不能单独支撑一个年份。史料互相矛盾时，不要选一个整数假装精确：`accuracy` 写 `disputed` 或 `approx`，并在 `birthNote` / `deathNote` 写明各说和取舍。

`docs/seats/` 里的试跑名单、检查线和目标人数是旧笔记。编译器不读它们，也不能拿来裁人。待收的人写在候选台账里。

## 两条流程

简表和详表用同一次 `npm run content`。简表的人就可以上轴。详表没写完，不挡简表发布。

### 简表

只出人物和上轴所需的信息：他是谁、哪一年、依据是什么、站在哪条脉络、放在哪条泳道。

1. 在 `pipeline/topics/<id>/candidates.json` 追加一条 `status: "pending"`。必填 `id`、`name`、`seat`（本专题已有泳道）、`anchor`（年份依据，一句话）、`sources`（至少一条 `classic` 或 `modern`）。
2. 核对锚点和出处后，运行 `npm run people:new -- <topic> <id>`，再改 `content/<topic>/<id>.md`。必填 `id`、`name`、`display`、`gender`、生卒与 accuracy、约略或异说的 note、`sources`（每条写 `kind`）、`polity`。`profile` 写 `brief`。正文先留空。还留在 `pipeline/registry/people/` 里的 44 人继续改那份 JSON，不要另建 Markdown。
3. 在该专题 `topic.json` 的 `people` 里加入 `{ "id", "lane" }`。`lane` 用候选的 `seat`。
4. 从 `candidates.json` 删掉这条 pending。确定不收的人改成 `status: "rejected"`，并写 `reason`。
5. 跑 `npm run content`。

### 详表

在已经上轴的人身上补读图所需的文字和关系。

1. 补 `title`、`tags`、`categories`。`bio` 两三句：身份、和轴上其他人的关系、为什么出现。Markdown 里 `bio` 写在正文，不要写进文首。存量 JSON 仍把 `bio` 写在字段里。
2. 在 `topic.json` 写有叙事意义的 `relations`。每条必须有 `note`。
3. 把 `profile` 改成 `full`。
4. 再跑 `npm run content`。写完 Markdown 先跑 `npm run people:format`，让文首顺序与模板一致。

没有关系的简表人物留在轴上。详表人物若仍没有任何关系，校验按专题汇总告警，不因此拒绝编译。

### 机器兜住什么

`npm run content:check` 会失败的情况：

- 候选 `pending` 缺锚点、缺可靠出处、`seat` 不是本专题泳道，或这个 `id` 已经写进登记 / 专题
- 候选 `rejected` 没有 `reason`，或人还留在该专题 `people` 里
- 生卒与 accuracy 矛盾，`disputed` 没有 note，生年晚于卒年
- 写了年份，但出处里没有 `classic` 或 `modern`（`kind` 省略视为 `classic`）
- 显式 `profile` 缺 `polity`；标了 `full` 却没有 `bio`；标了 `brief` 却已经写了 `bio`
- 显式 `profile` 的 `approx` 没有对应 note
- 人物 Markdown 缺文首、`profile`、`gender` 或出处 `kind`；`bio` 写进文首；字段不在模板里；`id` 与文件名不一致；格式与 `people:format` 的输出不一致；模板文件与 `pipeline/person-md.ts` 不一致
- 同一个人同时出现在 `content/<topic>/<id>.md` 和 `pipeline/registry/people/<id>.json`，或出现在两个专题目录里
- `content/<topic>.md` 索引和目录里的人物对不上

只告警、不失败的情况：还没标 `profile` 的存量 JSON 里，约略年份缺 note，或缺 `polity`；详表人物没有任何关系；已登记但没进任何专题。终端会另打一行收录进度：简表、详表、候选待核、不收、事件条数。

分类与 `primary` 现在直接写在人物源文件里，人工维护。旧的 `taxonomy` / `migrate` / `overrides` 迁移脚本已删除；迁移期间留下的缺口清单随脚本一并移除。

席位判得对不对、polity 脉络、note 有没有把异说写清、关系值不值得画，仍然由人判断。管线不设人数上限。

| 路径                          | 职责                                                                                                             |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `vocab/`                      | 地区、朝代、时代、主题、分类、政权、角色词表。新词先入表，再给专题挂上                                           |
| `content/<topic>/`            | 该专题的人物 Markdown。`content/<topic>.md` 是索引。模板在 `content/_template.md` 与 `content/_template-full.md` |

| `topics.json`                 | 专题发布顺序                                                                                                     |
| `schema/`                     | v1 合同、人物登记、候选台账、事件、专题与目录的 JSON Schema                                                      |

## 谁进专题

一个人进入专题，要占一个结构席位，并且有可引用的年份锚点（`exact`、`approx` 或 `disputed`）。标准帝王序列里的实际称帝者占帝王席。章节需要他讲清结构时，他也应该在底册里；章节名单不是另一道准入闸门。

年份锚点不够硬，不等于没有锚点。以下三种都算有：

- **异说并存**：两说皆可征 → `disputed` 加 `birthNote` / `deathNote`。
- **只有活动年或事件年**：史书只给「某年任某官」「某年见于某事」，不给生卒 → 以该年作 `approx`，并在 note 里写明「活动下限／上限，非寿数」。
- **只有卒年或只有生年**：有一端就够，另一端留空 `unknown`。

只有岁数（「卒年六十几」）而没有任何可系年的年份，才不进底册。史料模糊不是排除的理由——先收进来，把模糊写在 note 里。

席位各朝共用。一人在一个专题里只占一条泳道：

- **帝王**：标准序列，含实际称帝者。
- **后妃 · 外戚**：实际皇后、掌权后妃，以及废立、立储、政变的直接当事人。有年份锚点的都收。
- **宰相**：主持过一个执政期（宰相任上跨三个年头及以上），或主持过一件已经画上轴的制度或战事。只因官名相同、任期又短的，不自动进入。
- **将帅**：已画战争的双方主将，加上改变版图或藩镇格局的人。
- 多政权并立的朝代（如三国），宰辅、将帅席位按政权各计：魏、蜀、吴各有一套。
- **文学 · 艺术 · 宗教 · 技艺**：有传世作品，并且有年份锚点。
- **宗室**：进入储位之争、起兵或实际出镇的亲王。
- **对立面**：轴上事件的另一方首领，包括叛首、割据始祖，以及与本朝交兵并改变版图的外族首领。

世系表和宰相表里的名字，要先占到席位并有年份锚点，才进入底册。附传子侄要自己占到席位。孝友、隐逸、酷吏、四夷全录，要被席位点中才收。

只有任官年、没有生卒的，按活动年口径收：把任官年写成 `approx`，note 里写明这是任官年而非寿数，不要编成生卒。

泳道按职能命名，如「宰相」「将帅」。

章节 `people` 只标这一章要带着读者看的人。省略 `people` 就是这一章的时间窗里，底册上的人都能看见。全览同样不省略。不要为了把一章控制在某个人数而把已有锚点的人拒之底册外。

## 生卒

`exact | approx | disputed | unknown` 必须跟材料一致。

- 有异说：`disputed`，并写 `birthNote` / `deathNote`
- 不详：年份留空，accuracy 为 `unknown`
- 约略：`approx`，必须写 note，说明依据是什么
- 只有活动年／事件年：以该年作 `approx`，note 必须写明「活动下限／上限，非寿数」，不得让读者把它读成寿数
- 禁止用一个整数假装精确

生卒只写在人物登记里。专题不得覆盖年份。同一人出现在多个专题，只改 `lane`、`display`、`title`、`bio`、`tags`、`order`。

### 先秦卒年的两条纪年链

春秋专题并行两条纪年链，二者在周王世次处差约 4 年，分歧只在景王崩年一带。
选哪条要写明，不要默认全专题单链。

- **竹书链**：`raw/先秦/今本竹書紀年/晉紀.md` 是逐年编年，每王卒年记作「王陟」。自平王元年前 770 逐王推算在位年数。适用于竹书逐年明记卒年的国别——晋、齐等。所得即通行学术纪年。
- **经传链**：`raw/春秋/春秋左傳正義/` 全六十卷，左传公年可换算绝对年。适用于竹书未收的国别——楚、郑、卫等。春秋专题自 2026 年 10 月起，楚系用此链。

各专题所选链条记在 `docs/seats/<id>-seats.md` 的批次记录里。两条链都算出的年，若落在分歧带内，一律作 `approx` 并在 `deathNote` 写明依据，不取其一假装精确。

**取在位年数不能靠「谥号 + 年数窗口」扫史记散文**：谥号在国与代之间大量复用（晋文公取到 24、齐昭公取到 战国者），须按国限定卷次，且只认紧邻的「N年，X卒」。更常见的坑是纪年起点不同——史记楚世家「武王五十一年」是熊通自蚡冒元年起的纪年，不是武王在位长度，拿去顺推会差三十八年。

## 关系

重叠由生卒年算出来，不入库。只录有叙事意义的边：君臣、师承、亲族、同僚、敌对。

每条关系必须有 `note`，能一句话说清为什么值得画。管线可以以后输出「同时代候选」，但候选不得直接写成 `relations`。

## 章节

`views` 是产品，不能从词条生成。每章必须有：

- 时间窗 `from` / `to`
- 焦点人物 `focus`
- 教用户怎么读图的 `brief`
- 需要收窄时，写出 `people` 与 `events`（省略等于全收）

不设每章人数。`brief` 写这一章在图上能看见什么，不要写成时代概述。

## 文案

`bio` 两三句，服务读图：身份、和轴上其他人的关系、为什么出现在这一章。不要粘贴百科。

专题覆盖用于换角度，例如董仲舒在汉代专题称「董仲舒」，在儒学专题称「董子」。生卒仍是同一条登记。

## 出处

出处只存在管线源文件，不进入 v1 运行时 JSON。

一人至少一条。出处分三类，用 `kind` 标明：

| `kind`     | 写法                                              | 用途                                                 |
| ---------- | ------------------------------------------------- | ---------------------------------------------------- |
| `classic`  | 书名 + 卷篇，如《史记·周本纪》                    | 一手依据，可直接支撑年份                             |
| `modern`   | 现代考证的书名 + 页码或章节                       | 支撑 `approx` / `disputed`，须在 note 里说明取哪一说 |
| `database` | 数据库名 + 条目（Wikidata Q 号、CBDB 人物 id 等） | **只作候选**，见下                                   |

外部数据库（Wikidata、CBDB 等）的用法：

1. 只用来发现线索与对排异说——哪些人值得收、某人的年份有几种说法。
2. **不得直接抄进登记**。采信前须回到 `classic` 或 `modern` 核实；核实不了的，年份留空、accuracy 写 `unknown`，不要拿数据库里的数字凑整。
3. 参考过但没采信的，在 `birthNote` / `deathNote` 里写明「某库作 X 年，未采信，因……」，让后来人不必重查。
4. 登记里写了年份时，出处不能只有 `database`。管线会拒绝这种记录。`kind` 省略视为 `classic`。

存量 JSON 里 `kind` 省略时按 `classic` 处理。新的人物 Markdown 必须写出 `kind`。

## 词表与分面

- `region`：国家或地区，一个专题只能属一处
- `eras`：可多值。跨时段主题（儒学）把经过的时代都挂上
- `themes`：`dynasty`（王朝）、`thought`（思想）等。新主题先加词表

不要做成「国家 → 朝代 → 专题」的死树。三个分面编译进 `index.json` 的专题行，`eras` 或 `themes` 为空会被校验拒绝。当前站点的专题入口是顶栏专题下拉与快捷筛选，分面尚未做成筛选器（见 `docs/前端重设计.md` 第九节）。

## polity 的归属口径

polity 记的是「这个人站在哪条叙事脉络里」，不是血统、族属，也不是「他出生在哪朝」。

先记住一条：**polity 不会从生卒年推导出来。** `vocab/polities.json` 只有 `id` + `name`，没有起止年份；`compile.ts` 只把登记值原样抄进运行时 JSON。填错不会有任何校验报错，只能靠人判断。

两条规则：

1. **兴起期归入后世朝代。** 王朝建立之前的人物，只要属于该专题那条脉络，就标后起的朝代 id，不标过渡政权。元专题里铁木真、蒙哥、窝阔台、木华黎标 `yuan`；清专题里努尔哈赤、皇太极、多尔衮标 `qing`（`houjin` 已于 2026 年 10 月从词表移除）。
2. **与本朝脉络无关的草原政权另标族群政权。** 元明之际不以元朝臣属身份出现的蒙古势力标 `mongol`，如也先、俺答汗。

判定方法：看这个人的功业落在哪条脉络、和谁发生关系。**不是看他被几个专题收录**——专题收录是展示层的事，同一条登记进几个专题都不改 polity，「汉末群雄」这一层由东汉专题的 `qunxiong` 泳道表达，不是靠多写一个 `han`。同一个政权下的藩属与敌国才单独立词条（`xixia`、`liao-jin`、`tujue`）。

事件校验会发现人物叙事 `polity` 与事件时点政权不一致。允许的结构性差异集中写在 `pipeline/vocab/polity-compat.json`；该文件只放宽跨实体 warning，不授权修改人物 `polity`，也不把事件政权写回人物登记。新增兼容对必须写明 `reason`。

`categories` 与 `primary` 直接从人物源文件的词表字段读取，不再有推断脚本。补分类时改源文件，不要指望工具回填。

### 跨朝代人物

一人跨了几个政权，**不因此写成多值**。默认只标一条主脉络：

| 判据                     | 例子                           | polity                           |
| ------------------------ | ------------------------------ | -------------------------------- |
| 开国者的前朝岁月仍归新朝 | 刘邦（前 256 生，秦末起兵）    | `["han"]`，不写 `qin`            |
| 生于前朝、功业在后朝     | 李靖（571 生，隋臣唐将）       | `["tang"]`，不写 `sui`           |
| 过渡政权不立条目         | 铁木真、蒙哥、努尔哈赤、皇太极 | `yuan` / `qing`                  |
| 与本朝脉络无关的草原政权 | 也先、俺答汗                   | `mongol`                         |
| 汉末开国者归三国政权     | 曹操、刘备、孙权、孙坚、孙策   | `wei` / `shu` / `wu`，不写 `han` |

多值是例外，只在**同时占据两条叙事脉络**时使用。人数随收录变动，不设额度、也不必凑数：

| 例子   | polity             | 理由                           |
| ------ | ------------------ | ------------------------------ |
| 朱元璋 | `["yuan","ming"]`  | 元末群雄与明开国两条脉络都要他 |
| 伍子胥 | `["chu","wu-guo"]` | 楚、吴两条脉络都要他           |

`polity` 是有序数组，按时间先后排。

**跨朝代在站点上怎么体现**：同一条登记出现在多个 `topic.json`，泳道和文案各自覆盖——刘邦在秦专题 `lane:"han"`（作为秦的对立面），在汉专题 `lane:"emperor"`。专题覆盖字段只有 `lane / display / title / bio / tags / order`，不能覆盖 `polity`，也不能覆盖生卒。不要为了「让他在某个专题里显示成那一朝的人」去改 polity 或年份。

## 事件入口（规则以 `docs/事件线规则.md` 为准）

人物 PLAYBOOK 不定义事件字段或事件收录口径。事件的 canonical source 是 `content/events/<id>.md`；现有 `topic.json` 的 `events[]` 是冻结的旧 inline 输入，只能用于迁移盘点，不得继续扩写。军事与历史是同一事件库的两个 catalog，不是两套实体。

事件迁移必须先登记 `pipeline/events-migration-manifest.json`，并通过 `npm run events:migration:check` 的逐条冻结比对；经过证据、去重、taxonomy、引用和编译 gates 后，状态改为 `migration-approved` 才可落 canonical 文件。缺年份锚点、主出处或无法判断重复关系的条目保持 `evidence-needed`，不得以猜测补齐 `type`、`catalogs`、`polity`、`belligerents` 或 `sources`。新建事件先保持 `status: draft`，通过 publish gate 后才改为 `published`。不要把 `public/data/` 当源文件，也不要手改专题索引。
